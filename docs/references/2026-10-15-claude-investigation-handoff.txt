CODEX REVIEW HANDOFF — Orchestrate investigation (2026-10-15)

Context: Orchestrate is a Claude Code plugin (repo C:\Users\Josh\Desktop\GitHub\orchestrate,
v0.21.0, branch phase/0009-bench). Its goal: make Claude Code better at autonomous software
engineering for non-coders. Owner reports it made Claude worse: mechanical, process-heavy,
and, worst of all, it piles workarounds onto a design that fights the goal instead of
recognising the mismatch. Claude Code investigated read-only; nothing was changed.

What Orchestrate is:
- skills/orchestrate/SKILL.md (20 KB, a 10-section procedure), plain.md output style (5 KB),
  and a rules card (2.2 KB) re-injected each session and after each compaction.
- 9 hook commands: router, guard-agent (denies), guard-bash (regex shell parsing),
  context-check (every tool call), turn-check and persist-check (Stop blockers),
  ledger, postcompact-check.
- 8 agent personas.
- About 16k lines of hook/lib code plus 19k lines of tests; 30+ releases in 3 weeks.
About 27 KB of instructions are read per run.

Diagnosis (confidence):
- Blocking or denying hooks force goal-irrelevant work (high).
- Delegation bias costs 2–3x (high for cost, medium for quality).
- Instruction mass dilutes judgment (medium).
- Numeric rules replace judgment (medium).
- Rules accrete per incident (high).
- Re-implements native /goal, plan-file and CLAUDE.md re-injection, model frontmatter,
  permissions and sandbox (high that it does).
- Evals could not detect any of this, so "worse quality" is owner-reported, not measured (high).

Native Claude Code already covers: keep-going (/goal with a fresh evaluator, resume, limit
pause/resume, idle check-ins); compaction survival (root CLAUDE.md, auto memory, plan file,
skills up to 5k tokens each re-injected, SessionStart "compact" hook); plan mode; subagents
with per-agent model; /code-review (the docs warn reviewers over-report findings); permissions,
sandbox (WorktreeRemove covers only hook-created worktrees, so guard-bash's job is
only partly covered natively); claude plugin eval with a no-plugin baseline.
NOT covered: noticing mid-task that the architecture fights the goal.

Recommendation: drop Orchestrate's runtime. Build "D then C":
(D) one short skill (about 60 lines) with step-back judgment at the top, no procedure,
    no counters;
(C) plus one ADVISORY PostToolUse + PostToolUseFailure hook, about 150 lines, never blocking. It is silent unless
    it sees concrete churn: same file region edited 3+ times while the same check fails;
    same error signature after 2+ different fixes; special-case branches added in the loop;
    self-reverts. It then injects at most 300 characters naming the observed fact, once per
    signal, and can be switched off with an env var.
C ships only if it beats D; D only if it beats vanilla; otherwise the answer is
vanilla + /goal.
Why this time, when §7 failed: hypothesis only. (a) A rule buried in 27 KB of procedure is
ignored; (b) a model in a fix loop doesn't see itself looping, so an external observed fact
works where remembering a rule doesn't. The evidence counts against a rule BURIED in
procedure; a prominent rule alone is untested.
